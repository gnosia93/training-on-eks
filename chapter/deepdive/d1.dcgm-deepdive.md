## DCGM DeepDive ##


### nv-hostengine (호스트 엔진) ###
DCGM 호스트 엔진(nv-hostengine)은 DCGM의 핵심 데몬 프로세스로 DCGM 라이브러리를 감싸고 GPU와 통신하여 관련 메트릭을 수집 및 캐싱한다. 모든 DCGM 클라이언트(dcgmi, DCGM Exporter, Python/Go API 등)는 이 호스트 엔진을 통해 GPU 데이터에 접근하게 된다.
```
┌──────────────────────────────────────────┐
│           클라이언트들                      │
│  dcgmi    DCGM Exporter    Python API    │
│    │           │               │         │
│    └───────────┼───────────────┘         │
│                ▼                         │
│     nv-hostengine (호스트 엔진)             │
│     ├── 메트릭 수집/캐싱                     │
│     ├── 헬스 체크 실행                       │
│     ├── 정책 엔진                           │
│     └── 설정 관리                           │
│                │                         │
│                ▼                         │
│          NVML (드라이버 API)                │
│                │                         │
│                ▼                         │
│           GPU 하드웨어                     │
└──────────────────────────────────────────┘
```
두가지의 실행모드를 가지는데 
* Standalone: nv-hostengine이 독립 데몬으로 실행되고, 여러 클라이언트가 동시에 접속 가능하다. systemd 서비스로 등록하는 게 이 방식이다.
* Embedded: DCGM Exporter 같은 프로세스 안에 라이브러리로 내장되어 실행된다. (별도 데몬 불필요)
  
Kubernetes에서 DCGM Exporter를 쓸 때는 보통 embedded 모드로 동작해서 nv-hostengine을 따로 띄울 필요가 없다. 베어메탈이나 VM에서 직접 쓸 때만 standalone 데몬으로 실행한다. 
NVML 은 Nvidia Management Library 로 NVIDIA 드라이버에 포함된 C 기반 API 라이브러리이다. GPU 하드웨어 정보를 프로그래밍 방식으로 조회하고 관리할 수 있게 해준다. 


### DCGM 설치하기 ###

#### 1단계: NVIDIA 드라이버 확인 ####
AWS 콘솔에서 g6e 인스터스를 프로비저닝 한후 nvidia-smi 로 GPU 정보를 확인한다.  
```
nvidia-smi
```

#### 2단계: DCGM 설치 ####
```
# CUDA keyring 설치 (DCGM 패키지가 이 리포에 포함)
wget https://developer.download.nvidia.com/compute/cuda/repos/ubuntu2404/x86_64/cuda-keyring_1.1-1_all.deb
sudo dpkg -i cuda-keyring_1.1-1_all.deb
sudo apt-get update

sudo apt-get install -y datacenter-gpu-manager

sudo systemctl start nvidia-dcgm
sudo systemctl enable nvidia-dcgm
```

#### 3단계: 설치 확인 ####
```
# GPU 목록 확인
dcgmi discovery -l

# GPU 온도 한 번 조회
dcgmi dmon -e 150 -c 1

# 헬스 체크
dcgmi diag -r 1

# 여러 메트릭 동시 수집 (쉼표로 구분)
dcgmi dmon -e 150,155,252 -c 5
# 150: GPU 온도, 155: 전력, 252: 메모리 사용량. 5번 수집

# 수집 간격 변경 (밀리초)
dcgmi dmon -e 150 -d 1000
# 1초 간격으로 계속 수집 (Ctrl+C로 종료)

# 특정 GPU만 모니터링
dcgmi dmon -e 150 -i 0,1
# GPU 0번과 1번만

# 수집 가능한 전체 Field ID 목록 보기
dcgmi dmon -l
```
* dmon은 device monitor의 약자로 GPU 메트릭을 실시간으로 스트리밍해서 보여주는 서브커맨드.
* -e 150: 수집할 메트릭의 Field ID. 150은 GPU 온도(DCGM_FI_DEV_GPU_TEMP)
* -c 1: count. 1번만 수집하고 종료
* 자주 사용되는 Field ID 로는 150	GPU 온도, 155	전력 사용량, 203	GPU 사용률, 252	메모리 사용량, 1001	GPU Engine Activity, 1004	Tensor Core Activity, 1005	Memory BW Utilization 등이 있다.

#### 참고 - RHEL/Amazon Linux 2023에 설치 ####
```
sudo dnf config-manager --add-repo https://developer.download.nvidia.com/compute/cuda/repos/rhel9/x86_64/cuda-rhel9.repo
sudo dnf install -y datacenter-gpu-manager
sudo systemctl start nvidia-dcgm
sudo systemctl enable nvidia-dcgm
```

### GPU Diagnostics(진단) ###
dcgmi diag는 -r 옵션으로 진단 깊이를 1, 2, 3 중에 선택할 수 있고, 숫자가 올라갈수록 이전 레벨을 포함하면서 더 깊은 검사를 수행한다.
Level 1은 소프트웨어 환경 점검으로 GPU에 부하를 주지 않고 몇 초 만에 끝난다. NVML과 CUDA 라이브러리가 정상적으로 로드되는지, 디바이스 파일 접근 권한에 문제가 없는지, GPU persistence mode가 켜져 있는지, retired 메모리 페이지가 과도하지 않은지 등을 확인하느 것으로 일상적인 헬스체크 용도로 적합하다.  
Level 2는 Level 1에 하드웨어 검사를 추가하는 것으로, GPU 메모리 전체에 특정 패턴을 쓰고 다시 읽어서 비트 에러가 있는지 검출하고, GPU 내부 자체 진단을 통해 ECC 에러 같은 하드웨어 결함을 찾아낸다. 수 분 정도의 시간이 소요된다.
Level 3의 경우 Level 2에 통합 테스트와 성능 테스트를 추가한 전수 검사이다. PCIe 대역폭을 측정해서 Host와 GPU 간 데이터 전송 속도가 정상인지 확인하고, CUDA 코어에 실제 연산 부하를 걸어서 SM 처리량이 기대치에 부합하는지 검증한다. 또한 특정 연산 패턴으로 기대 성능 대비 실측을 비교하고, 최대 부하 시 전력 소비가 정상 범위 안에 있는지도 확인한다. GPU를 완전히 점유하면서 수 분에서 십 분 이상 걸리기 때문에, 정기 점검이나 신규 노드 투입 전 검증 용도로 쓰는 게 적합니다.

대규모 클러스터 환경에서는 ansible 또는 slurm 을 활용하여 GPU 를 진단할 수 있다.
#### Ansible 병렬 실행 ####
[dcgm-diag.yml]
```
- hosts: gpu_nodes
  become: yes
  serial: 20  # 한번에 20노드씩 (전체 묶이는 거 방지)
  tasks:
    - name: Run DCGM Level 3 Diagnostic
      command: dcgmi diag -r 3
      register: diag_result
      timeout: 600  # 10분 타임아웃

    - name: Save result to local
      local_action:
        module: copy
        content: "{{ diag_result.stdout }}"
        dest: "./diag_results/{{ inventory_hostname }}.txt"
```
```
mkdir -p diag_results
ansible-playbook -i inventory dcgm-diag.yml -f 20
```

#### SLURM Job으로 실행 ####
[dcgm-diag.sh]
```
#!/bin/bash
#SBATCH --job-name=dcgm-diag
#SBATCH --nodes=200
#SBATCH --ntasks-per-node=1
#SBATCH --gpus-per-node=8
#SBATCH --output=diag_results/%N.out
#SBATCH --exclusive

srun dcgmi diag -r 3
```
```
mkdir -p diag_results
sbatch dcgm-diag.sh
```

#### 컨테이너 환경 ####
```
apiVersion: batch/v1
kind: Job
metadata:
  name: dcgm-diag
  namespace: gpu-monitoring
spec:
  parallelism: 200
  completions: 200
  template:
    spec:
      nodeSelector:
        nvidia.com/gpu.present: "true"
      affinity:
        podAntiAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
          - labelSelector:
              matchLabels:
                job-name: dcgm-diag
            topologyKey: "kubernetes.io/hostname"
      containers:
      - name: dcgm-diag
        image: nvcr.io/nvidia/cloud-native/dcgm:3.3.7-1-ubuntu22.04
        command: ["/bin/sh", "-c", "echo \"=== $(hostname) ===\" && dcgmi diag -r 3"]
        resources:
          limits:
            nvidia.com/gpu: 8
        securityContext:
          privileged: true
      restartPolicy: Never
      tolerations:
      - key: nvidia.com/gpu
        operator: Exists
        effect: NoSchedule
  backoffLimit: 0
```
결과는 kubectl logs 로 확인한다.
```
# 전체 Pod 결과 한번에 수집
kubectl get pods -n gpu-monitoring -l job-name=dcgm-diag -o name | \
  xargs -I {} kubectl logs -n gpu-monitoring {} > dcgm-diag-all.log
```
핵심은 privileged: true와 GPU 전체 할당이다. Level 3 진단은 GPU를 독점해서 스트레스 테스트를 돌리기 때문에, 다른 워크로드가 해당 GPU를 쓰고 있으면 정확한 결과가 나오지 않는다. 현실적으로는 maintenance window 잡고 drain → 진단 Job 실행 (toleration 포함) → uncordon 순서로 하는 게 가장 깔끔하다. drain하면 기존 Pod도 다 빠지니까 GPU가 완전히 비워진 상태에서 정확한 진단이 가능하다.


### DCGM Profiling Module ###
Profiling 모듈은 GPU의 하드웨어 성능 카운터를 실시간으로 수집하는 모듈로, nvidia-smi가 보여주는 GPU Utilization보다 훨씬 세밀한 수준의 메트릭을 제공한다.
nvidia-smi의 GPU Utilization은 "GPU에서 커널이 실행 중인 시간 비율"만 보여주기 때문에, 실제로 GPU 자원을 얼마나 효율적으로 쓰고 있는지는 알 수 없다. Profiling 모듈은 이러한 문제점을 해결해 준다.

#### 수집 가능한 메트릭 ####
* SM Activity: SM(Streaming Multiprocessor)이 실제로 연산하고 있는 비율
* SM Occupancy: SM에 할당된 warp 수 대비 최대 warp 수의 비율
* Tensor Core Activity: Tensor Core가 활성화된 시간 비율
* FP16/FP32/FP64 Activity: 각 정밀도별 연산 유닛 사용률
* DRAM Activity: GPU 메모리 대역폭 사용률
* PCIe/NVLink Throughput: 인터커넥트 대역폭 사용량
dcgmi dmon -e 1001,1002,1003 같은 식으로 필드 ID를 지정해서 실시간 모니터링할 수 있고, DCGM Exporter를 통해 Prometheus로 내보내는 것도 가능하다.
예를 들면, 학습 Job의 GPU Utilization이 90%로 나오는데 Tensor Core Activity가 10%밖에 안 된다면, GPU는 바쁘게 돌고 있지만 실제로는 Tensor Core를 제대로 활용하지 못하고 있다는 뜻이므로 mixed precision 적용을 검토해볼 수 있다.
DCGM Profiling 모듈은 GPU 하드웨어에 내장된 성능 카운터를 읽기만 하는 거라서, 학습 워크로드에 미치는 성능 영향이 거의 없다. (1% 미만의 오버헤드)
다만 DCGM Profiling과 NVIDIA Nsight Systems/Nsight Compute 같은 프로파일링 도구를 동시에 사용하면 충돌이 발생할 수 있으므로 동시에 접근하면 메트릭이 부정확해지거나 에러가 날 수 있다.그래서 DCGM Profiling은 운영 환경에서 상시 모니터링 용도로 쓰고, Nsight 계열은 개발 환경에서 상세 디버깅 용도로 쓰는 식으로 분리하는 게 일반적이다.

### Health Monitor ###
Health Monitor는 GPU의 하드웨어 상태를 지속적으로 감시하다가 이상이 감지되면 알림을 주는 모듈로, 감시 대상은 크게 6가지 영역으로 나뉘어진다.
PCIe 상태를 감시해서 링크 속도 저하나 replay 에러가 발생하는지 확인하고, GPU 메모리 상태를 감시해서 ECC 에러(correctable/uncorrectable)가 누적되고 있는지, retire 메모리 페이지가 과도한지 추적한다. 또한 SM 상태를 감시해서 연산 유닛에 결함이 있는지 확인한다. 온도를 감시해서 thermal throttling이 발생하고 있는지 추적하고, 전력 상태를 감시해서 power throttling이나 비정상적인 전력 소비가 있는지 확인한다.

```
# 감시할 항목 설정 (GPU 그룹에 대해)
dcgmi health -g 1 -s mpi    # m=memory, p=pcie, i=inforom

# 전체 항목 감시
dcgmi health -g 1 -s a      # a=all

# 현재 상태 확인
dcgmi health -g 1 -c
```
상태 확인 결과는 Healthy, Warning, Failure 세 단계로 나온다. 예를 들어 ECC 에러가 소량 발생하면 Warning, 임계치를 넘으면 Failure로 보고된다.
운영 환경에서는 이걸 주기적으로 체크하는 스크립트를 돌리거나, DCGM의 Policy Manager와 연동해서 특정 상태가 감지되면 자동으로 콜백을 실행하도록 설정할 수 있다. 예를 들어 GPU가 Failure 상태가 되면 해당 노드를 SLURM에서 drain 처리하는 식이다.
